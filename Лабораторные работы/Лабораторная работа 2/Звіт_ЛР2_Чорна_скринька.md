# 3. СПЕЦИФІКАЦІЯ ТА ТЕКСТ ТЕСТОВАНИХ ПРОГРАМ

Для проведення тестування розроблено дві функції предметної області автоматизації кав'ярні.

## 3.1. Специфікація функції № 1: calculateCoffeeDiscount

1. **Назва функції:** `calculateCoffeeDiscount`.
2. **Призначення:** Автоматизований розрахунок величини відсоткової знижки на кавове замовлення клієнта.
3. **Вхідні параметри:**
   - `orderTotal` (`number`) — загальна сума замовлення у гривнях. Валідний числовий діапазон: від $1$ до $5000$ грн включно ($0 < orderTotal \le 5000$).
   - `cupsCount` (`number`) — кількість замовлених чашок кави. Валідний числовий діапазон: ціле число від $1$ до $30$ включно ($1 \le cupsCount \le 30$).
   - `hasLoyaltyCard` (`boolean`) — наявність активованої картки постійного клієнта (`true` або `false`).
   - `isHappyHour` (`boolean`) — ознака оформлення замовлення у період щасливих годин кав'ярні (`true` або `false`).
4. **Вихідні дані:**
   - Повертає ціле число (`number`):
     - `-1` — помилка валідації вхідних даних;
     - `20` — VIP-знижка $20\%$ при картці клієнта, щасливих годинах і чеку від $300$ грн;
     - `15` — знижка $15\%$ для клієнтів при замовленні від $5$ чашок або сумі від $400$ грн;
     - `10` — знижка $10\%$ у щасливі години або від $4$ чашок;
     - `5` — базова клієнтська знижка $5\%$;
     - `0` — замовлення без знижки ($0\%$).

## 3.2. Специфікація функції № 2: countCoffeeOrderTokens

1. **Назва функції:** `countCoffeeOrderTokens`.
2. **Призначення:** Посимвольний аналіз рядка чеку замовлень кав'ярні та підрахунок позицій напоїв, що починаються на задану літеру-префікс та задовольняють поріг мінімальної довжини.
3. **Вхідні параметри:**
   - `receiptText` (`string`) — рядок чеку з переліком найменувань напоїв через кому або пробіл.
   - `drinkPrefix` (`string`) — шукана початкова літера (порівняння без урахування регістру).
   - `minDrinkLength` (`number`) — мінімальна допустима довжина назви напою ($minDrinkLength \ge 1$).
4. **Вихідні дані:**
   - Повертає число (`number`):
     - `-1` — некоректна мінімальна довжина ($minDrinkLength \le 0$);
     - $\ge 0$ — кількість знайдених напоїв.

## 3.3. Текст тестованих функцій мовою TypeScript

```typescript
// Функція 1: Розрахунок знижки на замовлення кави
export function calculateCoffeeDiscount(
    orderTotal: number,
    cupsCount: number,
    hasLoyaltyCard: boolean,
    isHappyHour: boolean
): number {
    // Перевірка допустимих меж вхідних параметрів
    if (orderTotal <= 0 || orderTotal > 5000 || cupsCount <= 0 || cupsCount > 30) {
        return -1;
    }

    // Знижка 20% для постійних клієнтів у щасливі години від 300 грн
    if (hasLoyaltyCard && isHappyHour && orderTotal >= 300) {
        return 20;
    }

    // Знижка 15% за велике замовлення або суму
    if (hasLoyaltyCard && (cupsCount >= 5 || orderTotal >= 400)) {
        return 15;
    }

    // Знижка 10% у щасливі години або від 4 чашок
    if (isHappyHour || cupsCount >= 4) {
        return 10;
    }

    // Базова знижка за карткою клієнта
    if (hasLoyaltyCard) {
        return 5;
    }

    // Замовлення без знижки
    return 0;
}

// Функція 2: Підрахунок напоїв у чеку за префіксом та довжиною
export function countCoffeeOrderTokens(
    receiptText: string,
    drinkPrefix: string,
    minDrinkLength: number
): number {
    // Перевірка мінімальної довжини
    if (minDrinkLength <= 0) {
        return -1;
    }

    let matchCount = 0;
    let currentDrink = "";
    const targetPrefix = drinkPrefix.toLowerCase();

    for (let i = 0; i <= receiptText.length; i++) {
        const isEnd = (i === receiptText.length) || receiptText[i] === ' ' || receiptText[i] === ',';

        if (!isEnd) {
            currentDrink += receiptText[i];
        } else {
            if (currentDrink.length > 0) {
                const firstChar = currentDrink[0].toLowerCase();
                if (currentDrink.length >= minDrinkLength && firstChar === targetPrefix) {
                    matchCount++;
                }
                currentDrink = "";
            }
        }
    }

    return matchCount;
}
```

# 6. ПОРІВНЯЛЬНИЙ АНАЛІЗ МЕТОДІВ БІЛОЇ ТА ЧОРНОЇ СКРИНЬКИ

Оскільки в лабораторних роботах № 1 та № 2 досліджувалися ідентичні функції кав'ярні, проведено порівняння двох підходів тестування:

#### Таблиця 7. Зіставлення результатів тестування білою та чорною скринькою

| Критерій порівняння | Тестування білою скринькою (ЛР № 1) | Тестування чорною скринькою (ЛР № 2) |
| :--- | :--- | :--- |
| **Вихідна інформація** | Внутрішня структура програми (граф потоку керування, оператори, розгалуження). | Специфікація вимог, діапазони та контракти вхідних/вихідних даних. |
| **Кількість тестів** | **25 тестів** (100% покриття операторів, рішень, умов, комбінацій). | **47 тестів** (покриття класів, границь, евристик та причинно-наслідкових зв'язків). |
| **Пошук граничних дефектів** | **Середня.** Якщо границя оброблена гілкою, тест покриває її незалежно від оператора (`<` чи `<=`). | **Висока.** Тестуються точки безпосередньо на межах ($\pm 1$), що ловить дефекти операторів порівняння. |
| **Повнота перевірки вимог** | Не виявляє відсутній у коді функціонал, якщо він не був реалізований розробником. | Гарантує перевірку всіх вимог технічного завдання незалежно від наявності коду. |
| **Трудомісткість проектування** | Аналіз логіки коду, побудова графів передачі керування. | Формалізація таблиць класів, виділення границь та таблиць рішень. |

# 7. АНАЛІЗ РЕЗУЛЬТАТІВ ТА ВИСНОВКИ

У ході виконання лабораторної роботи № 2 було досліджено та практично застосовано методи тестування програмного забезпечення за принципом «чорної скриньки», а також реалізовано автоматизоване модульне тестування функцій предметної області кав'ярні мовою TypeScript:

1. **Аналіз ефективності методів чорної скриньки:**
   - Еквівалентне розбиття дозволило скоротити простір вхідних значень до 10 репрезентативних тестів з ізольованою перевіркою кожного невалідного класу.
   - Аналіз граничних значень (19 тестів) забезпечив всебічну перевірку критичних переходів, де найчастіше виникають помилки операторів порівняння.
   - Метод функціональних діаграм формалізував складені бізнес-правила знижок через таблицю рішень.

2. **Автоматизація тестування:**
   - Автоматизоване модульне тестування реалізовано за патерном Arrange-Act-Assert за допомогою вбудованого фреймворку `node:test` та модуля `assert`.
   - Усі 47 розроблених тестів успішно пройдено (100% PASS) як через тестовий раннер, так і через автономну програму-драйвер.

3. **Оцінка якості виконаної роботи:**
   - Порівняння з результатами ЛР № 1 підтвердило, що чорна скринька вимагає більшої кількості тестів (47 проти 25), проте гарантує виявлення невідповідностей технічному завданню та граничних помилок, які біла скринька може пропустити при неповному коді.
   - Робота виконана в повному обсязі відповідно до навчальних вимог.
