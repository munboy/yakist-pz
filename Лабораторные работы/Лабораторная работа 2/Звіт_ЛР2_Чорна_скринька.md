# 3. СПЕЦИФІКАЦІЯ ТА ТЕКСТ ТЕСТОВАНИХ ПРОГРАМ

Для проведення тестування розроблено дві функції предметної області автоматизації кав'ярні.

## 3.1. Специфікація функції № 1: calculateCoffeeDiscount

1. **Назва функції:** `calculateCoffeeDiscount`.
2. **Призначення:** Автоматизований розрахунок величини відсоткової знижки на кавове замовлення клієнта.
3. **Вхідні параметри:**
   - `orderTotal` (`number`) — загальна сума замовлення у гривнях. Валідний числовий діапазон: від $1$ до $5000$ грн включно ($0 < orderTotal \le 5000$).
   - `cupsCount` (`number`) — кількість замовлених чашок кави. Валідний числовий діапазон: ціле число від $1$ до $30$ включно ($1 \le cupsCount \le 30$).
   - `hasLoyaltyCard` (`boolean`) — наявність активованої картки постійного клієнта (`true` або `false`).
   - `isHappyHour` (`boolean`) — ознака оформлення замовлення у період щасливих годин кав'ярні (`true` або `false`).
4. **Вихідні дані:**
   - Повертає ціле число (`number`):
     - `-1` — помилка валідації вхідних даних;
     - `20` — VIP-знижка $20\%$ при картці клієнта, щасливих годинах і чеку від $300$ грн;
     - `15` — знижка $15\%$ для клієнтів при замовленні від $5$ чашок або сумі від $400$ грн;
     - `10` — знижка $10\%$ у щасливі години або від $4$ чашок;
     - `5` — базова клієнтська знижка $5\%$;
     - `0` — замовлення без знижки ($0\%$).

## 3.2. Специфікація функції № 2: countCoffeeOrderTokens

1. **Назва функції:** `countCoffeeOrderTokens`.
2. **Призначення:** Посимвольний аналіз рядка чеку замовлень кав'ярні та підрахунок позицій напоїв, що починаються на задану літеру-префікс та задовольняють поріг мінімальної довжини.
3. **Вхідні параметри:**
   - `receiptText` (`string`) — рядок чеку з переліком найменувань напоїв через кому або пробіл.
   - `drinkPrefix` (`string`) — шукана початкова літера (порівняння без урахування регістру).
   - `minDrinkLength` (`number`) — мінімальна допустима довжина назви напою ($minDrinkLength \ge 1$).
4. **Вихідні дані:**
   - Повертає число (`number`):
     - `-1` — некоректна мінімальна довжина ($minDrinkLength \le 0$);
     - $\ge 0$ — кількість знайдених напоїв.

## 3.3. Текст тестованих функцій мовою TypeScript

```typescript
// Функція 1: Розрахунок знижки на замовлення кави
export function calculateCoffeeDiscount(
    orderTotal: number,
    cupsCount: number,
    hasLoyaltyCard: boolean,
    isHappyHour: boolean
): number {
    // Перевірка допустимих меж вхідних параметрів
    if (orderTotal <= 0 || orderTotal > 5000 || cupsCount <= 0 || cupsCount > 30) {
        return -1;
    }

    // Знижка 20% для постійних клієнтів у щасливі години від 300 грн
    if (hasLoyaltyCard && isHappyHour && orderTotal >= 300) {
        return 20;
    }

    // Знижка 15% за велике замовлення або суму
    if (hasLoyaltyCard && (cupsCount >= 5 || orderTotal >= 400)) {
        return 15;
    }

    // Знижка 10% у щасливі години або від 4 чашок
    if (isHappyHour || cupsCount >= 4) {
        return 10;
    }

    // Базова знижка за карткою клієнта
    if (hasLoyaltyCard) {
        return 5;
    }

    // Замовлення без знижки
    return 0;
}

// Функція 2: Підрахунок напоїв у чеку за префіксом та довжиною
export function countCoffeeOrderTokens(
    receiptText: string,
    drinkPrefix: string,
    minDrinkLength: number
): number {
    // Перевірка мінімальної довжини
    if (minDrinkLength <= 0) {
        return -1;
    }

    let matchCount = 0;
    let currentDrink = "";
    const targetPrefix = drinkPrefix.toLowerCase();

    for (let i = 0; i <= receiptText.length; i++) {
        const isEnd = (i === receiptText.length) || receiptText[i] === ' ' || receiptText[i] === ',';

        if (!isEnd) {
            currentDrink += receiptText[i];
        } else {
            if (currentDrink.length > 0) {
                const firstChar = currentDrink[0].toLowerCase();
                if (currentDrink.length >= minDrinkLength && firstChar === targetPrefix) {
                    matchCount++;
                }
                currentDrink = "";
            }
        }
    }

    return matchCount;
}
```

## 4.4. Метод 4: Функціональні діаграми (причинно-наслідковий аналіз)

Виділено вхідні причини ($C_1..C_6$) та вихідні наслідки ($E_1..E_5$) розрахунку знижки кав'ярні:
- **Вхідні причини:** $C_1$ — наявна картка постійного клієнта; $C_2$ — замовлення у щасливі години; $C_3$ — сума чеку $\ge 300$ грн; $C_4$ — замовлено $\ge 5$ чашок; $C_5$ — сума чеку $\ge 400$ грн; $C_6$ — замовлено $\ge 4$ чашок.

| **Вихідна інформація** | Внутрішня структура програми (граф потоку керування, оператори, розгалуження). | Специфікація вимог, діапазони та контракти вхідних/вихідних даних. |
| **Кількість тестів** | **54 тести** (100% покриття операторів, рішень, умов, умов/рішень, комбінацій). | **67 тестів** (покриття класів, границь, евристик, таблиць рішень обох функцій). |
| **Пошук граничних дефектів** | **Середня.** Якщо границя оброблена гілкою, тест покриває її незалежно від оператора (`<` чи `<=`). | **Висока.** Тестуються точки безпосередньо на межах ($\pm 1$), що ловить дефекти операторів порівняння. |
| **Повнота перевірки вимог** | Не виявляє відсутній у коді функціонал, якщо він не був реалізований розробником. | Гарантує перевірку всіх вимог технічного завдання незалежно від наявності коду. |
| **Трудомісткість проектування** | Аналіз логіки коду, побудова графів передачі керування. | Формалізація таблиць класів, виділення границь та таблиць рішень. |

# 7. ВІДПОВІДІ НА КОНТРОЛЬНІ ЗАПИТАННЯ ДО ЛАБОРАТОРНОЇ РОБОТИ № 2

**1. Що таке тестування за методом «чорної скриньки»? Чим воно відрізняється від «білої скриньки»?**
*Відповідь:* Тестування за методом «чорної скриньки» (Black-Box Testing, поведінкове або функціональне тестування) — це підхід до тестування програмного забезпечення, за якого внутрішня структура, архітектура та вихідний код програми залишаються повністю невідомими тестувальнику або навмисно ігноруються. Тестування здійснюється виключно на основі специфікації вимог, інтерфейсів вхідних/вихідних даних та сценаріїв використання.  
*Ключові відмінності:*
- При «білій скриньці» тести розробляються за кодом програми для перевірки шляхів виконання та операторів. При «чорній скриньці» тести проектуються за технічним завданням для перевірки того, *що* робить система, а не *як* вона це робить.
- «Чорна скринька» здатна виявити повністю пропущені у коді бізнес-вимоги, які «біла скринька» ніколи не виявить, оскільки біла скринька тестує лише вже написаний код.
- «Чорну скриньку» можуть виконувати тестувальники без навичок програмування, моделюючи реальну поведінку кінцевих користувачів.

**2. Як формуються класи еквівалентності та скільки тестів вибирається з одного класу?**
*Відповідь:* Клас еквівалентності (Equivalence Class) — це підмножина значень вхідних даних програми, для яких реакція системи згідно зі специфікацією вважається однаковою, передбачуваною та однорідною. Припускається, що якщо тест успішно виконується для одного представника класу, то він так само успішно виконається для будь-якого іншого значення з цього класу, і навпаки (якщо виявиться дефект, він проявиться на будь-якому елементі класу).  
*Правила формування:*
1. Вхідний простір розбивається на **валідно-допустимі класи** (значення, передбачені штатною роботою) та **невалідні класи** (помилкові значення, значення поза допустимими межами, порушення типів даних).
2. З кожного виділеного класу еквівалентності обирається **рівно один тест** (один репрезентативний представник).
3. **Золоте правило тестування класів:** валідні класи можна поєднувати в одному тестовому випадку (покривати кілька валідних параметрів одним тестом), але **кожен невалідний клас повинен тестуватися в окремому ізольованому тесті**, щоб не допустити маскування однієї помилки іншою.

**3. Чому більшість помилок виникає саме на границях діапазонів значень?**
*Відповідь:* Статистика тестування та закон Майєрса свідчать, що найбільша концентрація програмних дефектів виникає саме на границях вхідних діапазонів значень (граничний ефект). Основні причини цього:
1. **Помилки операторів порівняння:** програмісти часто плутають строгі та нестрогі нерівності (наприклад, пишуть `>` замість `>=` або `<` замість `<=`), що призводить до некоректної поведінки саме в граничній точці.
2. **Помилка «на одиницю» (Off-by-One Error):** класична помилка індексації масивів та лічильників циклів (наприклад, цикл `for (i = 0; i <= n)` замість `< n`, вихід за межі діапазону).
3. **Неоднозначність у технічних завданнях:** у специфікаціях часто зустрічаються нечіткі формулювання («від 100 до 300 грн» — незрозуміло, чи включені числа 100 і 300).
4. Метод аналізу граничних значень (BVA) спеціально тестує саму границю та точки на $\pm 1$ крок від неї ($val-1, val, val+1$), що максимізує ймовірність виявлення дефектів за мінімальної кількості тестів.

**4. Які базові атрибути використовуються у тестових фреймворках MSTest та NUnit?**
*Відповідь:* У модульному тестуванні платформи .NET для маркування тестових сутностей використовуються спеціальні метадані — атрибути:
- **У фреймворку MSTest:**
  - `[TestClass]` — позначає клас, що містить модульні тести.
  - `[TestMethod]` — маркує конкретний тестовий метод для виконання у Test Explorer.
  - `[TestInitialize]` — метод, що автоматично виконується перед кожним тестовим методом (Setup).
  - `[TestCleanup]` — метод, що викликається після кожного тестового методу (Teardown).
  - `[ClassInitialize]` / `[ClassCleanup]` — одноразова підготовка та очищення ресурсів на рівні всього тестового класу.
  - `[ExpectedException(typeof(ArgumentException))]` — перевірка виклику очікуваного винятку.
- **У фреймворку NUnit:**
  - `[TestFixture]` — маркер тестового класу.
  - `[Test]` — маркер окремого тесту.
  - `[SetUp]` / `[TearDown]` — підготовка та очищення перед/після кожного тесту.
  - `[TestCase(1, 2, 3)]` — параметризований тест, що передає в один метод різні набори даних.

**5. Для чого призначений клас `Assert` і які його основні методи порівняння результатів?**
*Відповідь:* Клас `Assert` (у .NET MSTest/NUnit, а також аналогічний модуль `node:assert` у JavaScript/TypeScript) є ядром модульного тестування і реалізує заключну фазу **Assert** загальноприйнятого патерну **AAA (Arrange — Act — Assert)**.  
*Призначення:* перевірити істинність логічних тверджень та відповідність фактичного результату роботи коду очікуваному еталонному значенню. Якщо твердження хибне, клас `Assert` перериває виконання поточного тесту, генерує виняток невдачі (`AssertFailedException` або `AssertionError`) та передає фреймворку діагностичне повідомлення з різницею між очікуваним і фактичним значеннями.  
*Основні методи порівняння:*
- `Assert.AreEqual(expected, actual)` / `assert.strictEqual(actual, expected)` — перевірка точної рівності значень за значенням або посиланням.
- `Assert.AreNotEqual(notExpected, actual)` — перевірка нерівності значень.
- `Assert.IsTrue(condition)` / `Assert.IsFalse(condition)` — перевірка булевого виразу на істинність або хибність.
- `Assert.IsNull(object)` / `Assert.IsNotNull(object)` — перевірка значення на рівність `null`.
- `Assert.ThrowsException<TException>(() => ...)` / `assert.throws(...)` — перевірка того, що тестований блок коду викидає виняток заданого типу.
- `Assert.Fail("message")` — примусове завершення тесту зі статусом помилки.
