## 3.1. Функція № 1: `calculateCoffeeDiscount`
1. **Призначення:** розрахунок відсотка знижки на замовлення кави залежно від вартості, кількості чашок, наявності карти лояльності та періоду «щасливих годин».
2. **Вхідні параметри:**
   - `orderTotal` (number): сума замовлення в гривнях, допустимий діапазон $[1; 5000]$;
   - `cupsCount` (number): кількість чашок у чеку, допустимий діапазон $[1; 30]$;
   - `hasLoyaltyCard` (boolean): наявність картки постійного гостя (`true`/`false`);
   - `isHappyHour` (boolean): замовлення у період акції «Щасливі години» (`true`/`false`).
3. **Вихідні дані:**
   - ціле число відсотків знижки ($0$, $5$, $10$, $15$, $20$) або $-1$ при некоректних даних.
4. **Правила обчислення (Специфікація):**
   - Якщо `orderTotal <= 0` або `orderTotal > 5000` або `cupsCount <= 0` або `cupsCount > 30` $\to$ повертається `-1`.
   - Якщо гість має карту лояльності, замовлення зроблено у щасливі години і сума замовлення $\ge 300$ грн $\to$ знижка $20\%$.
   - Якщо гість має карту лояльності і при цьому замовив $\ge 5$ чашок або сума чеку $\ge 400$ грн $\to$ знижка $15\%$.
   - Якщо замовлення зроблено у щасливі години або замовлено $\ge 4$ чашок $\to$ знижка $10\%$.
   - Якщо гість має карту лояльності $\to$ базова знижка $5\%$.
   - В інших випадках $\to$ знижка $0\%$.

## 3.2. Функція № 2: `countCoffeeOrderTokens`
1. **Призначення:** посимвольний парсинг чека та підрахунок назв напоїв, які починаються на задану літеру і мають довжину не менше мінімального порогу.
2. **Вхідні параметри:**
   - `receiptText` (string): вихідний рядок замовлених позицій, розділених комами чи пробілами;
   - `drinkPrefix` (string): цільова початкова літера напою (нечутлива до регістру);
   - `minDrinkLength` (number): мінімально допустима довжина назви напою ($minDrinkLength \ge 1$).
3. **Вихідні дані:**
   - кількість знайдених напоїв або $-1$, якщо `minDrinkLength <= 0`.
4. **Правила обчислення (Специфікація):**
   - Якщо `minDrinkLength <= 0` $\to$ аварійне завершення та повернення `-1`.
   - Рядок чека переглядається посимвольно від $i = 0$ до $i = receiptText.length$.
   - Роздільниками слів вважаються пробіл `' '`, кома `','` або кінець рядка.
   - Якщо поточний символ не є роздільником $\to$ символ додається до поточного накопичуваного слова `currentDrink`.
   - При досягненні роздільника або кінця рядка перевіряється, чи накопичено слово:
     - Якщо довжина слова $> 0$, перевіряється умова фільтрації: довжина слова $\ge minDrinkLength$ ТА перший символ слова (без урахування регістру) збігається з шуканим `drinkPrefix`.
     - Якщо обидві умови виконуються $\to$ лічильник знайдених напоїв збільшується на $1$.
     - Слово очищується для обробки наступного елемента.
   - Після завершення обходу повертається загальна кількість знайдених напоїв.

```typescript
// Розрахунок знижки
export function calculateCoffeeDiscount(
    orderTotal: number,
    cupsCount: number,
    hasLoyaltyCard: boolean,
    isHappyHour: boolean
): number {
    // Валідація
    if (orderTotal <= 0 || orderTotal > 5000 || cupsCount <= 0 || cupsCount > 30) {
        return -1;
    }

    // Знижка 20%
    if (hasLoyaltyCard && isHappyHour && orderTotal >= 300) {
        return 20;
    }

    // Знижка 15%
    if (hasLoyaltyCard && (cupsCount >= 5 || orderTotal >= 400)) {
        return 15;
    }

    // Знижка 10%
    if (isHappyHour || cupsCount >= 4) {
        return 10;
    }

    // Знижка 5%
    if (hasLoyaltyCard) {
        return 5;
    }

    return 0;
}

// Підрахунок напоїв у чеку
export function countCoffeeOrderTokens(
    receiptText: string,
    drinkPrefix: string,
    minDrinkLength: number
): number {
    if (minDrinkLength <= 0) {
        return -1;
    }

    let matchCount = 0;
    let currentDrink = "";
    const targetPrefix = drinkPrefix.toLowerCase();

    for (let i = 0; i <= receiptText.length; i++) {
        const isEnd = (i === receiptText.length) || receiptText[i] === ' ' || receiptText[i] === ',';

        if (!isEnd) {
            currentDrink += receiptText[i];
        } else {
            if (currentDrink.length > 0) {
                const firstChar = currentDrink[0].toLowerCase();
                if (currentDrink.length >= minDrinkLength && firstChar === targetPrefix) {
                    matchCount++;
                }
                currentDrink = "";
            }
        }
    }

    return matchCount;
}
```

# 4. ПРОЕКТУВАННЯ ТА ВИКОНАННЯ ТЕСТІВ МЕТОДАМИ БІЛОЇ СКРИНЬКИ

## 4.0. Формалізація розгалужень та елементарних умов: обов'язкове правило $N_{\text{умов}} \ge N_{\text{рішень}}$

У тестуванні білою скринькою фундаментальним є розмежування понять **рішення** та **елементарної умови**:
- **Рішення ($D_i$)** — це булева керуюча точка програми (вираз у конструкції `if`, `while`, `for`), яка спрямовує потік керування в один із двох напрямків (`True` або `False`).
- **Елементарна умова ($C_{i.j}$)** — це просте атомарне порівняння (не містить логічних операторів `&&`, `||`), що входить до складу складного логічного виразу.

> **Фундаментальне математичне правило:**
> $$\mathbf{N_{\text{умов}} \ge N_{\text{рішень}}}$$
> Якщо розгалуження містить логічні зв'язки (наприклад, $a > b \lor b < c \implies p$), то рішення тут одне ($p$), але воно формується з двох атомарних умов ($a > b$ та $b < c$). Тому загальна кількість атомарних умов у будь-якій реальній програмі зі складними виразами **завжди строго більша** за кількість розгалужень.

### 4.0.1. Формалізація функції № 1 (`calculateCoffeeDiscount`)
Функція містить **5 рішень ($D_1..D_5$)** та **13 атомарних умов ($C_{1.1}..C_{5.1}$)**:

1. **Розгалуження $D_1$:** перевірка коректності параметрів `orderTotal` та `cupsCount`.
   - $C_{1.1}$: `orderTotal <= 0`
   - $C_{1.2}$: `orderTotal > 5000`
   - $C_{1.3}$: `cupsCount <= 0`
   - $C_{1.4}$: `cupsCount > 30`
   - *Рішення:* $D_1 = C_{1.1} \lor C_{1.2} \lor C_{1.3} \lor C_{1.4}$ (4 умови $\to$ 1 рішення).
2. **Розгалуження $D_2$:** перевірка права на знижку 20%.
   - $C_{2.1}$: `hasLoyaltyCard === true`
   - $C_{2.2}$: `isHappyHour === true`
   - $C_{2.3}$: `orderTotal >= 300`
   - *Рішення:* $D_2 = C_{2.1} \land C_{2.2} \land C_{2.3}$ (3 умови $\to$ 1 рішення).
3. **Розгалуження $D_3$:** перевірка права на знижку 15%.
   - $C_{3.1}$: `hasLoyaltyCard === true`
   - $C_{3.2}$: `cupsCount >= 5`
   - $C_{3.3}$: `orderTotal >= 400`
   - *Рішення:* $D_3 = C_{3.1} \land (C_{3.2} \lor C_{3.3})$ (3 умови $\to$ 1 рішення).
4. **Розгалуження $D_4$:** перевірка права на знижку 10%.
   - $C_{4.1}$: `isHappyHour === true`
   - $C_{4.2}$: `cupsCount >= 4`
   - *Рішення:* $D_4 = C_{4.1} \lor C_{4.2}$ (2 умови $\to$ 1 рішення).
5. **Розгалуження $D_5$:** перевірка базової знижки 5%.
   - $C_{5.1}$: `hasLoyaltyCard === true`
   - *Рішення:* $D_5 = C_{5.1}$ (1 умова $\to$ 1 рішення).

$$\mathbf{N_{\text{умов}} = 13 \ge N_{\text{рішень}} = 5 \quad (13 \ge 5)}$$

### 4.0.2. Формалізація функції № 2 (`countCoffeeOrderTokens`)
Функція містить **5 рішень ($D_1..D_5$)** та **8 атомарних умов ($C_{1.1}..C_{5.2}$)**:

1. **Розгалуження $D_1$:** перевірка коректності мінімальної довжини назви напою.
   - $C_{1.1}$: `minDrinkLength <= 0` (1 умова $\to$ 1 рішення).
2. **Розгалуження $D_2$:** умова продовження циклу `for`.
   - $C_{2.1}$: `i <= receiptText.length` (1 умова $\to$ 1 рішення).
3. **Розгалуження $D_3$:** ознака роздільника слів чи кінця рядка (`!isEnd`).
   - $C_{3.1}$: `i === receiptText.length`
   - $C_{3.2}$: `receiptText[i] === ' '`
   - $C_{3.3}$: `receiptText[i] === ','`
   - *Рішення:* $D_3 = \neg(C_{3.1} \lor C_{3.2} \lor C_{3.3})$ (3 умови $\to$ 1 рішення).
4. **Розгалуження $D_4$:** перевірка наявності накопиченого слова.
   - $C_{4.1}$: `currentDrink.length > 0` (1 умова $\to$ 1 рішення).
5. **Розгалуження $D_5$:** фільтрація напою за довжиною та префіксом.
   - $C_{5.1}$: `currentDrink.length >= minDrinkLength`
   - $C_{5.2}$: `firstChar === targetPrefix`
   - *Рішення:* $D_5 = C_{5.1} \land C_{5.2}$ (2 умови $\to$ 1 рішення).

$$\mathbf{N_{\text{умов}} = 8 \ge N_{\text{рішень}} = 5 \quad (8 \ge 5)}$$

# 6. АНАЛІЗ РЕЗУЛЬТАТІВ ТА ВИСНОВКИ

У процесі виконання лабораторної роботи здійснено практичне дослідження та порівняльний аналіз методів тестування програмного забезпечення за принципом «білої скриньки» на прикладі модулів бізнес-логіки автоматизації кав'ярні, розроблених мовою TypeScript. Побудовані алгоритми містять розгалуження зі складеними булевими виразами кон'юнктивного й диз'юнктивного типів, цикли та посимвольну обробку текстових чеків, що дозволило комплексно оцінити глибину та аналітичну вичерпність кожного зі структурних критеріїв тестового покриття.

Під час проектування тестових наборів було послідовно реалізовано п'ять методів тестування: покриття операторів, покриття рішень, покриття умов, покриття умов та рішень, а також комбінаторне покриття умов. Дослідження підтвердило наявність чіткої ієрархії надійності даних критеріїв. Базове покриття операторів забезпечує лише факт відсутності недосяжного коду, тоді як покриття рішень гарантує виконання кожної окремої гілки переходу. Окрему увагу приділено суворому дотриманню математичного правила $N_{\text{умов}} \ge N_{\text{рішень}}$, згідно з яким будь-яке складне розгалуження формується сукупністю елементарних булевих предикатів. Завдяки побудові деталізованих матриць тестів досягнуто 100% покриття для всіх 13 атомарних умов першої функції ($13 \ge 5$) та 8 умов другої функції ($8 \ge 5$), що унеможливило маскування помилок усередині складних логічних умов.

Застосування методу комбінаторного покриття умов дозволило верифікувати повні таблиці істинності для критичних керуючих виразів без виникнення комбінаторного вибуху. Вичерпний комбінаторний аналіз було спрямовано на найбільш відповідальні складені предикати: триелементну кон'юнкцію з 8 комбінацій та двоелементну диз'юнкцію з 4 комбінацій. Такий підхід забезпечив гранично високий рівень надійності верифікації за оптимальної кількості тестових прецедентів, повністю перекривши всі можливі стани взаємодії вхідних даних.

Практична валідація спроектованих тестових моделей виконана за допомогою автоматизованої програми-драйвера, яка реалізувала 70 тестів (56 тестів для функції розрахунку знижки та 14 тестів для посимвольного аналізу чеку). Співпадіння фактичних результатів виконання функцій з еталонними значеннями, визначеними суворо за специфікацією, досягло 100% без жодних розбіжностей. Отримані результати підтверджують високу ефективність структурного тестування білої скриньки у забезпеченні надійності та якості програмного забезпечення, а поставлені навчальні завдання виконано в повному обсязі.
