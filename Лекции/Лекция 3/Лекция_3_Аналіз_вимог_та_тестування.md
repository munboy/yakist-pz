## 🎯 Синопсис та ключові цілі лекції
Лекція розглядає процес аналізу та тестування вимог як фундамент для проектування якісного ПЗ. Обговорюються специфікація вимог (SRS, IEEE 830 / ISO стандарти), важливість однозначності, структурованості та використання загальноприйнятих акронімів (приклад з дипломними роботами студентів). Детально розбираються користувацькі історії (User Stories) та критерії прийнятності. Центральна частина — повна структура Тест-кейсу (Test Case) з прикладами для системи бронювання квитків «Укрзалізниці», додавання скріншотів та вкладень, а також відмінність тест-кейсів від чек-лістів (Checklists).

## ⏱ Детальний структурований конспект за темами та таймлайном
### `[00:00:02 - 00:08:00]` Вступ: зв'язок вимог та тестування. Стандарти SRS
- Технічне завдання та Специфікація вимог до ПЗ (SRS — Software Requirements Specification, IEEE 830).
- Стандартизована структура: Вступ, Загальний опис, Детальні вимоги.
- Роль документа як єдиної довідкової бази для всієї команди проекту.

### `[00:08:00 - 00:15:00]` Якість документації вимог і типові проблеми
- Важливість розділу скорочень, акронімів та термінів. Приклад: коли студент пише звіт чи диплом, він сам розуміє свої позначення, але без автора документ неможливо прочитати. Документ має бути самодостатнім.
- Атомарність, повнота, недвозначність та перевірюваність (тестованість) вимог.

### `[00:15:00 - 00:26:00]` Користувацькі історії (User Stories) та критерії прийнятності
- Формат користувацької історії: *«Як <роль у системі>, я хочу <дію/функціональність>, щоб <цінність/мета>»*.
- Різниця у потребах: приклад викладача і студента в системі «Лідер» (структура курсу, оцінювання).
- Acceptance Criteria (критерії прийнятності) як міст між бізнес-вимогами та тестами.

### `[00:26:00 - 00:40:00]` Анатомія та структура Тест-кейсу (Test Case)
- Обов'язкові поля повноцінного тест-кейсу:
  1. Test Case ID (унікальний ідентифікатор);
  2. Title / Summary (коротка, зрозуміла назва);
  3. Priority (пріоритет: High/Medium/Low);
  4. Preconditions (передумови: що має бути налаштовано перед початком);
  5. Test Data (вхідні тестові дані);
  6. Steps (покроковий алгоритм дій користувача);
  7. Expected Result (очікуваний результат — чітко сформульований);
  8. Postconditions (стан системи після завершення тесту);
  9. Status (статус виконання: Draft, Ready, Pass, Fail).

### `[00:40:00 - 00:55:00]` Практичний розбір тест-кейсів: сервіс продажу квитків
- Демонстрація реального документу: пошук залізничних квитків «Дніпро-Головний — Київ-Пасажирський».
- Вплив дати (дата в майбутньому vs дата, яка вже минула) на очікуваний результат.
- Негативні сценарії: станції, яких немає в базі даних (наприклад, зупинні платформи 193 км, 196 км).
- Вкладення та скріншоти (Attachments): використання схеми вагону зі скріншотами замість громіздкого словесного опису.

### `[00:55:00 - 01:13:51]` Чек-лісти (Checklists) vs Тест-кейси
- Чек-ліст як спрощений список перевірок (пункти 1, 2, 3... без детальних кроків та статусів).
- Коли використовувати чек-листи: для другорядних функцій (сортування за ціною, перегляд збережених квитків), для економії часу або при високій кваліфікації тестувальників.
- Порівняння трудовитрат на складання тест-кейсів та чек-лістів.

## 📖 Глосарій ключових термінів та визначень лекції
- **SRS (Software Requirements Specification):** Специфікація вимог до програмного забезпечення — комплексний документ, що повністю описує поведінку, інтерфейси та обмеження системи (IEEE 830).
- **User Story (Користувацька історія):** Короткий опис функції системи з точки зору кінцевого користувача: «Як [персона], я хочу [дія], щоб [користь]».
- **Тест-кейс (Test Case):** Набір вхідних даних, умов виконання, процедурних кроків та очікуваних результатів, розроблений для перевірки відповідності певної вимоги.
- **Чек-ліст (Checklist):** Структурований список ідей або перевірок, що підтверджують роботу функціоналу, без деталізації кроків виконання.
- **Критерії прийнятності (Acceptance Criteria):** Конкретні умови та правила, яким повинна відповідати функція, щоб бути прийнятою замовником.
