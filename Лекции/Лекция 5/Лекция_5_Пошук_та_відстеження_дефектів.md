## 🎯 Синопсис та ключові цілі лекції
Лекція детально розбирає роботу з дефектами програмного забезпечення: термінологічний ланцюжок Error -> Bug/Defect -> Failure, причини виникнення збоїв, стандартний життєвий цикл дефекту в баг-трекінгових системах (Jira, Redmine тощо), обов'язкові атрибути якісного Defect Report. Окремий акцент робиться на фундаментальному розмежуванні понять Severity (серйозність технічного впливу) та Priority (пріоритет виправлення для бізнесу) з практичними прикладами. Наприкінці лекції оголошується повітряна тривога.

## ⏱ Детальний структурований конспект за темами та таймлайном
### `[00:02:44 - 00:08:00]` Вступ: коли очікувані результати не співпадають з реальними
- Визначення ситуації виникнення дефекту під час прогону тестів.
- Базовий ланцюг: Помилка людини (Error) призводить до наявності дефекту у коді (Defect / Bug / Fault), який при виконанні викликає відмову системи (Failure).

### `[00:08:00 - 00:18:00]` Причини виникнення дефектів у програмних системах
- Неповні, суперечливі або мінливі вимоги.
- Помилки проектування структур даних та архітектури (приклад однозв'язних списків, розбіжність очікуваного списку та вектора).
- Помилки кодування, граничні випадки (off-by-one errors).
- Людський фактор, втома, неуважність, складність сучасних інтеграцій.

### `[00:18:00 - 00:30:00]` Життєвий цикл дефекту (Bug Life Cycle)
- Статуси дефекту: New (новий) -> Assigned (призначений) -> Open / In Progress (у роботі) -> Fixed (виправлений) -> Ready for Retest (готовий до повторної перевірки) -> Closed (закритий).
- Альтернативні гілки: Reopened (відхилений фікс, дефект не усунено), Rejected (не є багом / working as designed), Deferred (відкладено на наступні релізи), Duplicate (дублікат).

### `[00:30:00 - 00:44:00]` Звіт про дефект (Defect Report): поля та правила опису
- Заголовок (Summary): чітка формула «Що сталося? Де сталося? За яких умов?».
- Steps to Reproduce (STR): покроковий сценарій відтворення з точними вхідними даними. Важливість стабільної відтворюваності дефекту.
- Expected vs Actual Result: порівняння очікуваного та фактичного результату.
- Вкладення: логи, стек-трейси, скріншоти та відеозаписи відтворення.

### `[00:44:00 - 00:54:00]` Severity (Серйозність) vs Priority (Пріоритет)
- **Severity (Серйозність):** показує ступінь технічного впливу дефекту на працездатність системи (Blocker, Critical, Major, Minor, Trivial).
- **Priority (Пріоритет):** визначає терміновість виправлення дефекту для бізнесу (High, Medium, Low).
- **Комбінації-винятки:**
  * High Severity / Low Priority: краш програми у рідкісній функціональності, якою користуються раз на рік.
  * Low Severity / High Priority: граматична помилка в назві компанії на головній сторінці або зміщений логотип бренду.

## 📖 Глосарій ключових термінів та визначень лекції
- **Error (Помилка):** Помилкова дія людини (розробника, аналітика), що призводить до некоректного результату.
- **Defect / Bug (Дефект):** Недолік або вада в коді, документації чи конфігурації, яка може спричинити збій у роботі системи.
- **Failure (Відмова / Збій):** Невідповідність між фактичною поведінкою системи та її очікуваною поведінкою під час виконання.
- **Severity (Серйозність):** Ступінь негативного впливу дефекту на розробку чи функціонування системи загалом.
- **Priority (Пріоритет):** Черговість або терміновість, з якою дефект повинен бути виправлений розробниками.
- **Steps to Reproduce (STR):** Мінімальна послідовність кроків, необхідна для стабільного відтворення дефекту тестувальником або розробником.
